## What it covers

Three sections, reached from the side navigation:

- **Fleets** — create, rename or delete a fleet; assign a map to it (a map can only belong to one fleet at a time); and assign or unassign [[v-sherpa|Sherpa]] robots to it.
- **Assets** — the inventory the Fleets section draws from: the map library, and every Sherpa robot together with the hardware ID and API key that identify it.
- **Users & Permissions** — add, edit or delete users and roles, and toggle exactly which Fleets, Map, Users, Sherpa and Summon Button actions each one is allowed.

Deleting a fleet, a Sherpa or a user is restricted to the Support role and cannot be undone.

## How it relates to Fleet Manager

A change made in Deployment Manager is reflected in [[v-fleet-manager|Fleet Manager]] automatically — a new or deleted fleet, a Sherpa assignment, and a user's access and permissions all appear on the Fleet Manager side without a separate sync step.

## How a robot is actually connected, in practice

Deployment Manager has an "Activate Config" screen for setting a robot's Wi-Fi without SSH access. In practice it isn't used: a field engineer instead brings a Wi-Fi dongle for the robot's initial bring-up, connects to the robot directly over SSH, and edits its configuration file by hand — adding the Fleet Manager's IP address and the [[v-sherpa|Sherpa]]'s certificate file, which authenticates its communication with Fleet Manager. A self-hosted (non-AWS) Fleet Manager needs that certificate generated by a script and loaded manually; an AWS-hosted one generates and applies it automatically. Only once this is done does the robot switch from the engineer's dongle onto the customer's own network.

## Map versions and fleet assignment

A map has one live, auto-saving **draft** at a time, plus a history of named **published** versions. A published version is frozen — to edit it, a new draft has to be created from it first. A fleet is assigned exactly one map and one version of it, and every Sherpa in that fleet runs that same version; there is no way to run different robots in one fleet on different map versions. Moving a fleet to a genuinely different map (not just a new version of the same one) has no direct "swap" action — every Sherpa has to be unassigned first, then reassigned under the new map.

:::gap title="An unshipped internal request"
The support engineer who described this said they had already asked their own development team to move versioning from the map to the fleet, specifically so a fleet could be temporarily repointed at a different use case (for example, if production drops and a robot is needed elsewhere) without fully re-doing the map assignment. As of this transcript, that change had not shipped.
:::

## Multiple fleets, one server

A single Fleet Manager server commonly hosts several independent fleets — for separate plants, or separate customers entirely. Which fleets a given user can see and switch between, in the fleet dropdown, is scoped by their login, not by which server they're connected to.

:::gap
